# AI usage log

Running notes for the "How I used AI" section of FIXES.md. Add one entry per step.

| Step | What I asked | What I accepted | What I changed or rejected, and why |
|---|---|---|---|
| Planning | Analyze the assignment and make a full plan | 3-phase, step-by-step plan; PostgreSQL outbox for pushes; conditional SQL updates for races | Chose Supabase for production Postgres instead of Render Postgres (Render's free DB expires after 30 days). Renamed the project to BadalBooking so it can't mix with an older attempt. |
| 1.1 Skeleton | Create the solution skeleton | Solution, API and test project, `/ping`, smoke test, `.gitignore` with secret rules | |
| 1.1 Question | Why local Postgres instead of connecting Supabase now? | Local Docker Postgres for development, tests and CI; Supabase only for the deployed app (Phase 3), same migrations for both | Accepted. Reasons: frequent schema changes, disposable test data, speed, free-tier limits, CI must not need production secrets. |
| 1.2 Database | Local Postgres, entities, DbContext, first migration | Guid v7 ids, integer halalas, server-only price via `Booking.Create`, stored payment deadline, xmin concurrency token, check constraints, `app` schema | Reviewed the generated migration: EF had put its history table in `public` (exposed by Supabase's REST API), so it was moved into `app`. Used `docker run` because the compose plugin isn't installed locally. |
| 1.2 Secrets | Put all current secrets in a `.env` with comments on where each one goes | Git-ignored `.env` (chmod 600) + committed `.env.example`; small `DotEnv` loader used only in Development; real env vars always win | Moved the connection string out of `appsettings.Development.json` so no committed file holds one. Wrote a 30-line loader instead of adding a package. Production values stay in Render/GitHub/Vercel, never in `.env`. |
| 1.3 Auth | Register, login, JWT | Customer-only registration, PBKDF2 hashing, HS256 JWT with only `sub`/`role`/`jti`, unique-index-based duplicate check, same 401 + equal timing for unknown email vs wrong password, per-IP rate limit, ProblemDetails errors | |
| 1.3 Deploy-readiness | "Backend on Render, frontend on Vercel — make sure it works when deployed" | Bind to Render's `PORT`; trust `X-Forwarded-For` only when `RENDER=true`; strict CORS with exact origins, startup fails on `*`/non-https in production | Caught that behind Render's proxy every user would share one IP, so the login rate limit would lock everyone out. Proxy header handling must be re-checked on the live Render URL in step 3.3. |
| 1.4 Bookings | Create, list, get bookings with ownership checks | Request DTO with only `pilgrimName`; owner from the JWT; price from `Booking.Create`; ownership filter inside the SQL query; 404 (not 403) for other users' bookings; bounded page size; performer id hidden from customers | Chose to silently ignore extra JSON fields (price, status, customerId) rather than reject them; the demo shows the stored row is still 500 SAR and owned by the caller. |
| 1.5 Payment | Idempotent payment with a simulated gateway | `IPaymentGateway` + clearly-labelled simulator; `Idempotency-Key` header scoped per customer; conditional `UPDATE ... WHERE status='PendingPayment' AND deadline > now` inside a transaction with the payment insert; partial unique index "one Succeeded payment per booking"; 422 when a key is reused for another booking; startup refuses any provider other than Simulated | **Bug found during the demo:** with 10 parallel requests using the SAME key, 2 got 409 instead of the original payment (a retry could read the booking after the first request committed but before re-checking its key). No double charge happened, but retries must always get the same answer. Fixed by re-checking the key before any 409; verified over 5 rounds of both races. Goes into FIXES.md. |
| 1.6 Cancel + Accept | Customer cancel, performer seed, available list, accept | Accept = one conditional `UPDATE ... WHERE status='Paid' AND performer_id IS NULL`; cancel = conditional updates for PendingPayment / Paid-and-unassigned, with a simulated refund in the same transaction; performer created only from server config (never promotes an existing customer); performers see only id, pilgrim name and date | Added a `Refunded` payment status + migration (a paid booking cancelled before acceptance must give the money back). Demo note: the login rate limit correctly blocked my own rapid demo logins, so the race demo used `RateLimits__AuthPerMinute=1000` for that run only. |
| 1.7 Expiry job | Background job that expires bookings unpaid for 30 minutes | `BackgroundService` with `PeriodicTimer`, runs once at startup (catch-up after Render's free-tier sleep), new DI scope per run, errors logged and retried next tick; one SQL `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED LIMIT n) AND status='PendingPayment' RETURNING` so paid/cancelled bookings are never touched and several instances can share the work | **Bug found during the demo:** the SQL aliased the returned columns as `"Id"`/`"CustomerId"`, but EF's snake_case convention expects `id`/`customer_id`. The UPDATE committed, then reading the result failed, so the job changed rows without knowing which ones (step 2.5 needs that list for push notifications). The first demo only checked statuses and looked fine; checking the worker log revealed it. Fixed and re-verified with 2 instances: 350 expired, reports add up to exactly 350, 0 errors. |
| 1.8 Tests | Integration tests on a real Postgres container | 41 xUnit tests via `WebApplicationFactory` + Testcontainers (postgres:17, same migrations as production); fake clock for the 30-minute rule; race tests release all requests at once and assert both the HTTP results and the database rows; regression test for the step 1.5 same-key bug; tests never read `.env` or touch the local DB | Predicted before running that moving the fake clock would break JWT checks (tokens issued at fake time, validated against the real clock). Changed production code so token lifetime is checked with the injected `TimeProvider` — one clock for the whole app. Verified: without that change 32/41 tests fail, with it 41/41 pass. Ran the suite 6 times: 41/41 every time (~12 s). |
| 2.1 Firebase setup | Load the Firebase Admin SDK safely | Key copied into git-ignored `.env` by a script that never printed it; `FirebaseSetup` reads only `Firebase__ProjectId` + `Firebase__ServiceAccountJson`, rejects a key from another project, never logs the JSON; required in Production, optional locally/in tests | Verified with a throwaway read-only script (not in the repo): connected to project `badal-booking`, 1 Email/Password user. The downloaded key file is still in ~/Downloads — the user should move it out or delete it. |
| 2.2 Firebase sign-in | `POST /auth/firebase`: verify ID token, find/create user, return our JWT | Admin SDK `VerifyIdTokenAsync(checkRevoked: true)`; `firebase_identities` table (unique uid, unique user); rules: known uid → that user; email must be verified; Performer email → refused; existing Customer → linked once; else new Customer; retry once on concurrent first sign-in; same 409 message for performer/already-linked so it doesn't reveal roles | **Changed the brief:** the assignment only requires a verified email for *linking*; I require it for *every* new Firebase sign-in, otherwise someone could create an unverified Firebase account with another person's email and claim it here first. Demo used genuine Firebase ID tokens (temporary users created and deleted by a throwaway script): all 9 scenarios behaved as designed, including revoked tokens → 401. |
| 2.3 Test web client | Browser page for real Firebase sign-in and push | Static `web/` site (deployable to Vercel): Firebase JS SDK 13.0.0 from gstatic, sign-in / sign-up / email verification, ID-token exchange at `/auth/firebase`, FCM token + foreground and background (service worker) notifications; API JWT kept in memory only; all server text rendered with `textContent` | Pinned Firebase JS 13.0.0 instead of the newest 13.1.0 (released only 2 days earlier). The public web config was read from the existing Firebase web app; it is not a secret. Verified page loads with no console errors and a cross-origin call from :5173 reaches the API (CORS OK). The actual sign-in was left to the user, since it sends a real password to Google. |
